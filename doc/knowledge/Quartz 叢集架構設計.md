# Quartz 叢集架構設計

在最常見的 Spring Boot 架構下是 1:1，但在系統架構設計上「不強制是 1:1」，兩者完全可以解耦。

關鍵在於：Quartz 實例的本質只是一個跑在 JVM 內部的執行緒集合（Thread Pool）。我們可以選擇讓它跟著每個 AP（應用伺服器）一起啟動，也可以將它獨立出來或選擇性啟用。

目前有以下三種常見的部署架構：
1. 嵌入式同構部署（1:1 模式，最常見）
2. 獨立排程服務部署（M:N 或專屬叢集模式）
3. 同一程式碼庫，透過配置開關決定（非 1:1 的靈活實作）

---

## 一、嵌入式同構部署（1:1 模式，最常見）

- **架構**：如果線上部署了 5 台業務 AP（如 5 個相同的 Spring Boot Pod / 實例），每一台 AP 都啟用了 Quartz 並連向同一個 MySQL 資料庫。
- **比例**：AP : Quartz = 1 : 1（5 台 AP 對應 5 個 Quartz 叢集節點）。
- **優點**：架構最單純，無需額外維運獨立的排程集群；叢集自動具備 5 節點的高可用與容災。
- **缺點（核心瓶頸）**：
  - **水平擴展反效果**：當為了應對使用者流量將 AP 橫向擴展（Scale out）到 20 台時，Quartz 節點也瞬間變成 20 個。這 20 個節點每隔數秒都在對 `QRTZ_LOCKS` 執行 `SELECT ... FOR UPDATE`，AP 越多，資料庫鎖競爭（Lock Contention）與連線數壓力越大。
  - **資源干擾**：若某個重度批次 Job 耗盡了 CPU/記憶體，會直接拖慢該台 AP 處理一般使用者 HTTP 請求的效能。

---

## 二、獨立排程服務部署（M:N 或專屬叢集模式）

- **架構**：將排程任務從一般業務 AP 抽離，獨立成一個專門負責定時任務的微服務（例如 `order-job-service`）。
  - **業務 AP（處理 Web 請求）**：部署 10 台，完全不啟動 Quartz。
  - **排程 AP（專跑 Quartz）**：只部署 2~3 台組成高可用叢集。
- **比例**：AP : Quartz 不是 1:1。
- **優點**：
  - **資源隔離**：重型排程運算完全不影響在線使用者的 HTTP API 響應。
  - **保護資料庫**：Quartz 節點數固定在 2~3 台，資料庫的 `TRIGGER_ACCESS` 鎖競爭維持在極低水平，不再隨業務 AP 擴容而暴增。

---

## 三、同一程式碼庫，透過配置開關決定（非 1:1 的靈活實作）

若不想拆成兩個獨立專案，可以使用同一份 Spring Boot 映像檔，但透過環境變數或 Spring Profile 決定該節點是否啟動 Quartz：

```yaml
# 預設關閉（一般 AP 節點）
spring:
  quartz:
    auto-startup: false 

# 僅在特定排程節點開啟 (如啟動參數加上 -Dspring.quartz.auto-startup=true)
```

- **例如**: 部署 10 台 Pod 中，9 台為一般 AP（`auto-startup: false`），只有 2 台被指定為排程執行者（`auto-startup: true`）。此時 AP 與 Quartz 的比例為 10 : 2。

---

## 結論

在小型或中型系統中，為了省事通常直接採用 1:1。但一旦 AP 數量因為 Web 高並發需求擴展到較大規模，強烈建議切換為獨立排程節點（非 1:1），將 Quartz 節點數量控制在 2 至 3 台（既保證了高可用容災，又避免了過多節點無謂爭搶資料庫行鎖）。
